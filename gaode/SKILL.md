# 周边去哪儿

完成一次“理解需求 → 查询高德地点 → 核验步行路线 → 筛选并回答”。每个推荐都是从用户同一起点出发的独立备选，不串联为多站行程。仅依赖运行环境提供的高德工具，不要求用户安装服务、提供 API Key、运行脚本或导出日志。

## 1. 明确约束

- 提取城市、起点坐标、地点类型、步行时间上限、推荐数量、排除项和排序偏好。平台已给起点坐标时直接使用，不重新定位或用同名地点替换起点。坐标按工具定义传入，通常为 `经度,纬度`，保留原精度。
- 推荐上限 `K = min(用户要求的数量, 3)`；未指定数量时为 3。用户只要 1 或 2 个时严格遵守；不要为了凑数加入不合格地点。
- 用户给出的分钟上限 `T` 转为秒 `limit_seconds = T × 60`。未指定时限时不添加默认硬限制。“不超过／以内”按小于等于；明确“少于”按严格小于。其他明确距离、预算、类型等条件也必须满足。
- 区分硬条件与偏好：“必须营业”“只要免费”是硬条件，“最好安静”是偏好。不能核实的硬条件不能宣称满足；可核验其他条件但不满足全部硬条件的地点不进入正式推荐。无法核实的软偏好标注“未核实”，仍可根据已核实条件推荐。
- 用户说“优先近一点／距离近”时按实际步行距离升序、再按步行耗时升序；“最快／时间短”及未指定排序时按步行耗时升序、再按距离升序。其他偏好仅用工具确实提供的证据排序；数据缺失时简短说明并采用步行耗时排序。

正常评测输入已有城市和坐标，直接执行，不重复询问。若实际输入确实缺少起点，只在可用高德工具能唯一定位时使用其结果；否则请求具体坐标，禁止猜测。未给具体类型但明确“随便逛逛”时，可搜公园、咖啡馆等少量常见类别并说明选择。

## 2. 适配高德工具并搜索

先查看当前环境实际暴露的工具说明与参数结构，使用已配置的高德 MCP。工具可能带服务名前缀；按能力和实际名称匹配，不凭空调用工具，不传结构中没有的字段。

| 能力 | 常见工具名 | 关键参数与用途 |
|---|---|---|
| 周边搜索 | `maps_around_search` | `location` 为起点坐标，`keywords` 为地点类型，`radius` 为米制搜索半径 |
| 地点详情（需要补信息且工具可用时） | `maps_search_detail` | 用搜索返回的 `id` 获取同一 POI 的坐标、地址、类型等 |
| 步行路线 | `maps_direction_walking` | `origin` 始终为原起点，`destination` 为该 POI 的真实坐标 |

参数类型遵从当前 schema；例如有的版本将 `radius` 定义为字符串，应传 `"1500"` 而不是数值。若工具返回 MCP `content` 文本块中的 JSON，应读取其中的业务数据；如直接返回结构化对象，则直接读取。检查工具错误及业务状态，成功状态下的空数组才是无结果，不能把错误响应当作无结果。

以用户类型为搜索关键词，例如“咖啡馆”“川菜”“公园”。不把整句偏好作为关键词，也不随意限制成某个品牌。默认先搜半径 1500 米；有时限时可用 `max(1000, min(5000, T × 100))` 米作为首轮检索范围。这个半径仅用于发现候选，绝不用于判定步行可达或推算步行时间。用户明确限定搜索半径时遵守其范围。

按 POI ID 去重；缺 ID 时用名称、地址和坐标共同识别，同名不同门店不得合并。保存名称、地址、ID、坐标、类型等原始证据，核对类型、城市及排除条件。不要把名称相似的地点或上级商场直接当作所需门店。

## 3. 补齐坐标，再逐个核验步行路线

**周边搜索不保证返回坐标或距离。** 有些版本只返回 `id/name/address/typecode`。若缺少 `location`，先用该 POI ID 查询地点详情；缺地址或类型不明确时也按需补查。不得从记忆、名称或另一门店推测坐标。详情工具不可用或补查仍缺坐标时，排除该地点，继续其他候选并记录原因。地址仍缺失但坐标和路线可核验时，可保留并将地址写为“高德未返回详细地址”，不得编门牌号。

优先核验类型符合、信息可用的候选。首批通常选择 6–8 个；只有搜索确实返回距离时，才用该距离安排查询顺序，不能假设搜索结果已按距离排序。对首批选中的候选完成路线核验后统一排序，不要一够 K 个就停止首批核验。

对每个候选调用步行路线工具，始终使用同一原起点和该候选坐标。将每个结果绑定到对应 POI，避免串用不同门店的路线。不要使用驾车、骑行、直线距离或自行设定的步速代替步行路线。

常见响应为 `route.paths`，部分封装可能是顶层 `paths`，以实际返回为准。读取每条完整路径的总 `distance` 和总 `duration`，通常单位为米、秒；若工具明确给出其他单位，先换算。数字字符串可转为数值，但空字符串、null、空数组、缺失字段、负值或无法确认单位的值均不能视为有效的 0。缺总耗时或总距离、空路径或错误响应的地点不能进入推荐，不自行用路段、直线距离或经验补出总值。

同一地点有多条有效步行路径时，先筛选符合用户硬条件的路径，再按用户排序偏好选择一条；距离与耗时必须取自**同一条路径**。保存未取整的米数和秒数。

## 4. 按原始数据筛选和排序

- 先核验地点类型和其他硬条件，再将路线原始秒数与 `limit_seconds` 比较；没有时限时无需这一项过滤。明确限制步行距离时也用路线总距离比较。
- 例如 15 分钟以内表示最多 900 秒：900 秒符合，901 秒不符合，即使显示时都可能被取整成 15 分钟，也不得放行 901 秒。
- 对所有已核验且合格的独立地点，按第 1 节的排序规则排序，再取前 K 个。搜索距离只用于发现候选，不用于最终排序。并列时保持稳定顺序。
- 若数量不足，先核验现有尚未检查的有效候选；必要时最多补充一轮搜索：使用保持原类型的同义词，或在用户未限定半径时适度扩大检索范围，再合并去重。不降低地点类型要求、不删除排除项，也不擅自放宽用户步行时限。
- 通常核验不超过 12 个独立候选即可形成轻量推荐；达到此范围或工具预算后如实返回已验证结果。回答限定为“本次查询并核验的地点”，不声称覆盖全城或保证全局最近。

## 5. 处理失败、缺失和无结果

- 临时超时、限流或服务错误：对失败请求有限重试，通常重试 1 次；明确限流等待要求且运行预算允许时遵守。单个地点失败不使其他成功结果失效；同一服务持续失败时停止重复调用。
- 参数错误：按实际 schema 修正后重试 1 次。鉴权失败、工具未配置等不可恢复错误直接说明所需服务不可用，不索要密钥，不伪造数据。
- 已找到地点但路线失败或缺有效耗时：说明“找到了相关地点，但未能核实步行路线”，不能改称附近没有地点，也不能提供假定的步行时间。
- 有效路线全部超时：正式推荐为 0，说明“本次已核验的候选均超过 X 分钟”；可建议放宽时限，但不把超时地点列为符合条件的推荐。
- 搜索成功但无结果：说明“本次搜索范围内未找到该类型地点”，可建议扩大范围或更换类型。不要将有限搜索描述成“附近绝对没有”。
- 合格数量不足：只给实际合格数量，并据实指出是超时、类型不符、信息不足或部分查询失败；不得将未核验地点算作不合格或已合格。
- 安静、排队、营业状态、价格、评分等仅在返回数据能够支持时陈述。营业时间字段不自动等于此刻营业；没有实时证据就标“营业状态未核实”。不把环境偏好写成事实，不用品牌常识填补证据。

## 6. 简洁呈现

先一句话说明本次找到的数量、用户明确的时限（若有）以及排序依据，然后用表格或列表给出：

| 地点名称 | 地址 | 预计步行距离 | 预计步行时间 | 推荐理由 |
|---|---|---|---|---|

每行是本次高德返回并通过核验的真实地点，不输出示例或占位行。名称保留门店信息；地址仅使用高德返回内容。步行距离可直接显示原始米数，步行时间将秒数准确换算成“X 分 Y 秒”（整分钟可省略秒），标明为高德路线预计值。**先用原始值判定是否达标，再格式化显示。** 不把剩余秒数向下取整以掩盖超时。

推荐理由限一句，依据已核实的类型、路线和偏好，例如说明它在本次已核验合格候选中步行距离较短、位于时限内。没有证据时不要写“口碑好”“环境安静”“无需排队”“正在营业”或保证全局最近。

表后仅补充必要说明：数量不足的具体原因、相关偏好“未核实”、部分路线失败等。零推荐时不输出空表，直接解释并给一个可行的放宽建议。若提到候选数或成功核验数，必须与实际记录一致。

发出答案前核对：每个地点及地址有高德来源；每条路线起点相同、终点匹配；距离与耗时来自同一有效步行路径；原始值满足所有硬条件；数量不超过 K；排序与数据一致；未核实信息没有被写成事实。无需向用户展示内部记录或工具日志。
